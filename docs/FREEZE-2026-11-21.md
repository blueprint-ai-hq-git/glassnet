# FREEZE INCIDENT 2026-11-21 15:04:31: THE GPU FELL OFF THE BUS, AND THE ONE RESULT THAT SURVIVED (captured 15:07, documented 19:07)

## What happened, from the kernel's own words

The machine did **not** reboot - it stayed up with the GPU gone. Captured from the live boot before the display was lost:

```
15:04:31 onwards   nvidia-modeset: ERROR: GPU:0: Error while waiting for GPU progress     (36 occurrences)
15:05:29           NVRM: _issueRpcAndWait: rpcSendMessage failed with status 0x0000000f for fn 7
15:05:29           NVRM: _issueRpcLarge: rpcSendMessage failed with status 0x0000000f for fn 76!
15:05:29           NVRM: nvAssertFailedNoLog: Assertion failed: 0 @ rpc.c:2090
afterwards         the driver query: "Unable to determine the device handle for GPU0: 0000:01:00.0: Unknown Error"
                   the driver query: "No devices were found"
```

`status 0x0000000f` is a driver-RPC timeout: the card stopped answering the driver. That is consistent with a hung GPU rather than a
driver crash or a thermal event, and it explains why the display died while the rest of the system kept running - this assistant kept
working through it on CPU.

**Was it fixable without a reboot?** No. Recovering a hung GPU needs a module reload or a PCIe function-level reset, both of which need
root. The reboot at **15:09:06** restored it: the card came back and reports normally to the driver.

## Both instruments failed, and both are my fault

1. **The freeze watchdog was not running.** Its log stops at **2026-11-20 21:29:55** - a full day before the event - and its unit was
   absent from the user systemd directory. So the one thing built to catch exactly this recorded nothing.
2. **The event's telemetry had to be scraped by hand** from `journalctl -b 0` minutes after the freeze, and `journalctl` dies with a
   reboot. That is why this capture happened at 15:07 and not at 15:05.

**Both fixed:** the watchdog script is re-created at `~/.local/bin/freeze-watch.sh` with a systemd user unit
(`glassnet-freeze-watch.service`), enabled and **active**, writing one line every 14 s to **ext4** (not the damaged NTFS project disk) and
counting `NVRM`/`nvidia-modeset` errors so the next event is timestamped from inside the system:

```
2026-11-21 19:06:24 | avail=... cached=... swapfree=... dirty=13MB | load 7.20 4.79 3.97 | card reporting normally | nvrm_err=0
```

## The evidence that could still name the cause

There is a **real kernel dump from the earlier crash today at 08:46**:
`/var/crash/202611210846/dump.202611210846` (**204 MB**) plus its `dmesg`. It is root-only (`-rw------- root whoopsie`), so reading it
needs the owner's password. It is the first hard artifact of a freeze this project has ever had, and it is worth analysing.

## What the freeze cost, and what it did not

**Lost:** three unfinished arms (3-digit and 5-digit subtraction, 8-digit addition) - relaunched as `bt2`.

**Not lost - and this is the notable part:** the 3-digit subtraction arm had already **trained to 100.0% token accuracy**
(`step 5600/6000 loss 0.0002 token acc 100.0%`) before the freeze killed it at the scoring step. Training and its logs are flushed to
disk as they go, so a hard freeze costs the *unfinished* evaluation, not the run.

**Verified intact after reboot:** project `99b7f07`, public repo = remote `2c4987c`, off-drive safety copy **2.2 GB**, every carry result
(`CARRY-r1`, `CARRY3-r2`, `CARRY-SCALE2-r2`) unchanged, and the freeze capture itself copied to ext4 with a matching sha256.
